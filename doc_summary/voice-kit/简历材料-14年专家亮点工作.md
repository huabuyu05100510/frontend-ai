## 三、亮点工作的核心陈述

### 3.1 一句话定位（简历标题）

```
跨端语音技术基建 — 解决实时对话竞态、延迟观测、跨端复用三大系统性难题
```

### 3.2 核心亮点（简历必写，按重要性排序）

#### 亮点1：形式化方法解决竞态（最重要，体现专家深度）

**问题**：实时对话中，用户打断AI时，正在排队的音频块会继续播放，产生"上一句尾巴"。

**传统方案的局限**：
- `stopPlayback()`：只能切当前块
- 锁/状态标记：无法证明正确性，可能有遗漏场景

**我的方案**：
1. 设计responseId门控机制：每个播放块携带单调id
2. interrupt()四步原子操作：自增门控 → 丢弃陈旧块 → stop当前 → 等待完成
3. **TLA+形式化规约**：写规约 `converse.tla`，模型检验证明"interrupt完成后不存在陈旧播放事件"

**专家价值**：
- 会TLA+的前端 < 1%
- 不是"我解决了问题"，而是"我证明了方案的正确性"

**简历一句话**：
```
设计responseId门控的Barge-in状态机，TLA+形式化规约证明无竞态泄漏
```

---

#### 亮点2：统计学理论支撑的性能观测（体现理论深度）

**问题**：传统前端监控用"滑动窗口200样本估算p99"，但方差极大，不同窗口算出来可能差一倍。

**为什么传统方案是"伪命题"**：
- 样本量固定，窗口外数据丢失
- p99对极端值敏感，窗口滑动会导致估算跳变
- 没有误差界，不知道算出来的值有多准

**我的方案**：
1. 设计chunk_id RTT回显协议：客户端打id，服务端ack，精确到单帧
2. 用HDR Histogram：对数线性桶，保留所有样本分布信息
3. **理论保证**：任何样本量下，p99误差 ≤1%
4. 可合并：多客户端数据可在服务端聚合

**专家价值**：
- 知道"为什么滑动窗口不行"（统计学理解）
- 知道"HDR Histogram为什么行"（算法理解）
- 不是调库，而是有理论支撑

**简历一句话**：
```
首创chunk_id RTT协议+HDR Histogram延迟观测，p99误差≤1%，替代滑动窗口估算的统计学伪命题
```

---

#### 亮点3：底层API深度运用（体现底层理解）

**问题**：主线程被UI渲染抢占时，音频采集丢帧。

**ScriptProcessorNode的本质问题**：
- 回调在主线程执行
- 主线程被阻塞 → 音频回调延迟 → 缓冲区欠载 → 丢帧
- 这是**平台限制**，不是"优化"能解决的

**AudioWorklet的本质差异**：
- 独立音频线程（AudioWorkletGlobalScope）
- 与主线程**零竞争**，主线程阻塞不影响音频
- 这是**架构层面的隔离**，不是API升级

**SharedArrayBuffer零拷贝**：
- 双SAB架构：数据SAB + 索引SAB（避免伪共享）
- Atomics.wait/notify同步（理解原子操作）
- 主线程100%负载下仍稳定20ms帧

**专家价值**：
- 理解"线程模型的本质差异"（不是API差异）
- 理解"原子操作、内存模型、伪共享"（底层原理）
- 不是"用Worklet替代ScriptProcessor"，而是"架构隔离"

**简历一句话**：
```
AudioWorklet+SAB零拷贝环形缓冲，Atomics同步，主线程100%负载下稳定20ms帧
```

---

#### 亮点4：架构层面的跨端抽象（体现架构思维）

**问题**：浏览器、小程序、Electron的API完全不同，传统方案要写3遍代码。

**传统方案**：
- 条件编译：`if (isWx) { ... } else { ... }`
- 分支逻辑散落各处，维护成本高
- bug修复要同步3处

**我的方案**：
1. 定义接口契约：`IAudioCapture / IAudioPlayer / ITransport / IStorage`
2. 依赖注入：`createScene({ capture: WebAudioCapture })`
3. 场景层只依赖接口，**永不直接import平台代码**
4. eslint-plugin-boundaries强制检查依赖方向

**专家价值**：
- 不是"API封装"，而是"架构隔离"
- 不是"写适配器"，而是"定义契约"
- 类型系统强制，编译期就能发现违规

**简历一句话**：
```
三端跨端抽象，接口契约+依赖注入，同一套状态机零修改复用
```

> 
> 30个npm包公开发布，核心reducer只有6KB。"

### 5.2 追问应对（展现专家深度）

**Q: 你说TLA+证明，具体怎么做的？**

> "我写了TLA+规约文件 `converse.tla`，定义了状态空间：
> - 变量：currentResponseId、scheduled队列、playing状态
> - 操作：enqueue、interrupt、onended
> 
> 然后用TLC模型检验器跑所有可能的状态转换，验证不变量：
> ```
> ALWAYS ~(interrupt完成后 ∧ 存在陈旧播放事件)
> ```
> 
> 模型检验跑了约10万次状态转换，没有发现反例。这比'我测试了一下没问题'要有说服力得多。"

**Q: 为什么HDR Histogram比滑动窗口好？**

> "这是统计学问题。滑动窗口估算p99有两个理论缺陷：
> 
> 第一，样本量固定200个，窗口外的历史数据丢失了，你不知道整体分布；
> 
> 第二，p99对极端值敏感，窗口滑动时，一个极端值进入或离开窗口，估算值会跳变。
> 
> HDR Histogram用对数线性桶，把值域分成不同精度的桶：
> - 小值（0-10ms）：细粒度桶，精度0.1ms
> - 中值（10-100ms）：中粒度桶，精度1ms
> - 大值（100-1000ms）：粗粒度桶，精度10ms
> 
> 这样既保留了所有样本的分布信息，又控制了内存占用。而且它支持合并，多客户端的直方图可以在服务端聚合，这是滑动窗口做不到的。"

**Q: AudioWorklet和ScriptProcessor有什么本质区别？**

> "本质区别是线程模型：
> 
> ScriptProcessor的回调在主线程执行，主线程被React渲染、JavaScript执行抢占时，音频回调会延迟，缓冲区欠载，就丢帧了。这是平台限制，不是'优化'能解决的。
> 
> AudioWorklet运行在独立的音频线程（AudioWorkletGlobalScope），与主线程零竞争。主线程阻塞1秒，Worklet仍然以20ms节奏稳定运行。
> 
> 这是架构层面的隔离，不是API升级。理解这一点，你才知道为什么不能用ScriptProcessor。"

**Q: 你说跨端抽象，具体怎么设计的？**

> "核心是接口契约和依赖注入：
> 
> 我定义了6个核心接口：IAudioCapture、IAudioPlayer、ITransport、IStorage、IClock、IResampler。
> 
> 场景层（比如scene-transcribe）通过工厂函数接收实现：
> ```ts
> createTranscribeScene({
>   capture: new WebAudioCapture(),     // 浏览器
>   // capture: new WxRecorderCapture(), // 小程序
> })
> ```
> 
> 场景层的代码永不直接import平台API，只依赖接口。
> 
> 我用eslint-plugin-boundaries强制检查依赖方向，core包如果import了DOM API，编译期就会报错。
> 
> 这样架构隔离是强制的，不是靠'自觉'。"
