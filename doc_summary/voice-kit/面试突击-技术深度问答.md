## 一、音频采集层（AudioWorklet）

### Q1: 为什么用AudioWorklet而不是ScriptProcessorNode？

**问题本质**：主线程与音频线程的竞争关系

**ScriptProcessorNode的问题**：
- 回调在**主线程**执行
- 主线程被UI渲染、React reconcile、JavaScript执行抢占
- 音频回调被延迟 → 缓冲区欠载 → 音频断续、丢帧
- `bufferSize` 不可动态调整（固定256/512/1024/2048）

**AudioWorklet的方案**：
- **独立音频线程**（AudioWorkletGlobalScope）
- 与主线程**零竞争**，20ms帧节奏稳定
- 通过 `MessagePort` 或 `SharedArrayBuffer` 与主线程通信
- `bufferSize` 动态可调

**代码证据**（adapter-web/src/capture.ts:72-76）：
```typescript
const ctx = new AudioContext({ latencyHint: 'interactive' });
await ctx.audioWorklet.addModule('/capture-processor.js');
const worklet = new AudioWorkletNode(ctx, 'vk-capture-processor', {
  processorOptions: { targetRate: 16000, capacity: 64000 }
});
```

**备选方案**：
- 回退 `ScriptProcessorNode`（仅用于不支持Worklet的老浏览器，如UC浏览器）
- 但要文档化已知问题：主线程抖动会丢帧

**权衡**：
- AudioWorklet需要单独的processor文件（CDN部署）
- 首次加载有模块解析延迟（~50ms），但可通过 `<link rel="preload">` 优化

### Q2: SharedArrayBuffer零拷贝如何实现？

**问题本质**：避免每帧 `postMessage` 的序列化开销

**传统方案的问题**：
```typescript
// 每帧都要拷贝
worklet.port.postMessage({ type: 'chunk', data: new Int16Array(320) });
// → 结构化克隆 → 主线程接收 → GC压力
```

**零拷贝方案**：
1. **双SAB架构**：
   - `dataSAB`：环形PCM缓冲（Int16，容量4秒）
   - `indexSAB`：独立索引（Int32，写指针+读指针）

2. **Worklet写入**：
```javascript
// 在 AudioWorkletProcessor 中
const data = new Int16Array(this.dataSAB);
const idx = new Int32Array(this.indexSAB);
data[writePos % capacity] = sample;
idx[0] = writePos;  // 发布写指针
```

3. **主线程读取**：
```typescript
// 零拷贝读取
const data = new Int16Array(this.dataSAB);
const idx = new Int32Array(this.indexSAB);
const writePos = Atomics.load(idx, 0);
const readPos = Atomics.load(idx, 1);
// 直接访问data，不拷贝
```

**代码证据**（adapter-web/src/capture.ts:90-96）：
```typescript
if (canSAB) {
  this.dataSAB = new SharedArrayBuffer(this.capacity * 2);
  this.indexSAB = new SharedArrayBuffer(16 * 4);
  processorOptions = { ...processorOptions, dataSAB: this.dataSAB, indexSAB: this.indexSAB };
}
```

**为什么分离索引SAB？**
- 避免伪共享（false sharing）
- 数据SAB是Int16粒度，索引SAB是Int32粒度
- 读写路径无依赖，Atomics操作只在索引SAB上

**降级策略**：
- 无 `crossOriginIsolated` 时回退 `MessagePort.postMessage`
- iOS Safari需要COOP/COEP头才能启用SAB

### Q3: 如何保证主线程100%负载下音频不丢帧？

**问题本质**：主线程抖动不影响音频线程

**核心设计**：
1. **AudioWorklet在独立线程**：主线程被阻塞，Worklet仍以20ms节奏运行
2. **环形缓冲吸收抖动**：容量4秒，主线程延迟1秒仍能恢复
3. **Atomics.wait通知**：主线程醒来后批量读取，不丢帧

**代码证据**（adapter-web/src/capture.ts:194-221）：
```typescript
const tick = () => {
  const writePos = Atomics.load(idx, 0);
  const chunkId = Atomics.load(idx, 2);
  if (chunkId !== lastChunkId) {
    // 批量读取积压帧
    let len = writePos - readPos;
    if (len < 0) len += this.capacity;
    // ... 零拷贝读取
  }
  setTimeout(tick, 10);  // 主线程轮询
};
```

**极端情况**：
- 如果主线程阻塞 > 4秒：环形缓冲覆盖 → 数据丢失
- 但这是极端场景，正常UI渲染不会阻塞这么久

## 二、流式ASR去重

### Q4: 为什么需要四路径去重？

**问题本质**：火山引擎bigmodel协议的累积模式

**协议特性**：
- **累积模式**：每帧发送完整文本（带标点修正）
- **Partial乱序**：网络抖动导致后发先至
- **终结修正**：Final可能与最后一个Partial不同

**朴素方案的问题**：
```typescript
// 直接替换
setText(newText);
// → 用户看到闪烁：你好 → 你好吗 → 你好
```

**四路径分类器**（scene-transcribe/src/reducer.ts:160-214）：

| 路径 | 条件 | 动作 | 示例 |
|------|------|------|------|
| A | 新文本=旧文本+扩展 | 增量更新 | "你" → "你好" |
| B | 新文本⊂旧文本 | 跳过（回滚） | "你好吗" → "你好" |
| C | ≥70%前缀重叠 | 续接 | "你吃饭" → "你好吗" |
| D | 以上都不满足 | 新建卡片 | 说话人切换 |

**代码证据**：
```typescript
// A路径：扩展
if (normNew.startsWith(normLast) && normNew.length > normLast.length) {
  cards[lastIdx] = { ...last, text: action.text };
}

// B路径：回滚
if (normLast.startsWith(normNew) && normNew.length < normLast.length) {
  return state;  // 跳过
}

// C路径：前缀重叠
const overlap = prefixOverlap(last.text, action.text);
if (overlap >= 0.7) {
  cards[lastIdx] = { ...last, text: action.text };
}
```

**为什么是70%？**
- 经验值，基于实测数据调优
- 太低（50%）→ 错误合并
- 太高（90%）→ 正常续接被误判为新卡片

### Q5: 如何保证Reducer是纯函数？

**问题本质**：可测试性、可回放、无竞态

**纯函数定义**：
- 相同输入永远产生相同输出
- 无副作用（无I/O、无Math.random、无Date.now）
- 不修改输入参数

**实现策略**（scene-transcribe/src/reducer.ts:111-154）：

```typescript
export function transcriptionReducer(
  state: TranscriptionState,
  action: TranscriptionAction
): TranscriptionState {
  switch (action.type) {
    case 'PARTIAL':
      return applyPartial(state, action);  // 纯函数
    case 'FINAL':
      return applyFinal(state, action);    // 纯函数
    // ...
  }
}

// 时间戳从外部注入
action: { type: 'PARTIAL', text: '你好', ts: Date.now() }
// Reducer内部不调用Date.now()
```

**测试优势**：
```typescript
// 任意时刻重放
const state1 = transcriptionReducer(initial, action1);
const state2 = transcriptionReducer(state1, action2);
// 多次运行结果相同
```

**如果需要随机数？**
- 从action注入：`action: { type: 'RANDOM', seed: 12345 }`
- Reducer内部用确定性伪随机：`mulberry32(seed)`

### Q6: 如何处理说话人分离？

**问题本质**：引擎返回的speaker_id不可信，需要客户端稳定映射

**引擎问题**：
- `speaker_id` 可能是 "0", "1", "2"...
- 同一会话内稳定，但跨会话不一致
- 用户需要看到 "发言人 1", "发言人 2" 这种稳定标签

**客户端方案**（scene-transcribe/src/reducer.ts:288-297）：
```typescript
// 按出现顺序分配标签
const labels = new Map<string, string>();
labels.set('0', '发言人 1');
labels.set('1', '发言人 2');

// 颜色稳定映射
function getSpeakerColor(speakerKey: string): string {
  const hash = djb2(speakerKey);  // 确定性哈希
  return SPEAKER_PALETTE[hash % 12];
}
```

**djb2哈希为什么稳定？**
```typescript
function djb2(str: string): number {
  let hash = 5381;
  for (let i = 0; i < str.length; i++) {
    hash = ((hash << 5) + hash) + str.charCodeAt(i);
  }
  return hash >>> 0;
}
// 同一字符串永远返回同一数字
```

## 三、播放与Barge-in

### Q7: TTS播放为什么会有咔哒声？

**问题本质**：`AudioBufferSourceNode.start()` 无参数调度

**错误写法**：
```typescript
for (const chunk of chunks) {
  const src = ctx.createBufferSource();
  src.buffer = decode(chunk);
  src.start();  // 立即播放 = "now"
  await new Promise(r => src.onended = r);  // 等待结束
}
```

**问题**：
- `start()` 无参数 = 从 `ctx.currentTime` 开始
- 前一块结束 → 解码下一块 → 调度下一块：中间有间隙
- 间隙 → 咔哒声

**时间调度方案**（adapter-web/src/player.ts:69-84）：
```typescript
const now = ctx.currentTime;
const start = this.nextStartTime === 0
  ? now + this.safetyEpsilon
  : Math.max(now + this.safetyEpsilon, this.nextStartTime);

src.start(start);
this.nextStartTime = start + buf.duration;  // 记录预期结束时间
```

**为什么用 `Math.max`？**
- 防止 `nextStartTime` 落后于当前时间
- 如果落后，说明调度延迟，跳过该块并记录gap

### Q8: Barge-in竞态如何消除？

**问题本质**：打断时三层队列都会泄漏旧音频

**三层队列**：
1. **等待队列**：已接收但未解码的音频块
2. **解码队列**：正在解码的Promise
3. **播放队列**：已调度但未播完的AudioBufferSourceNode

**朴素方案的问题**：
```typescript
function interrupt() {
  currentSource?.stop();  // 只能切当前块
  // 等待队列的块会继续播放！
}
```

**responseId门控方案**（adapter-web/src/player.ts:106-131）：
```typescript
interrupt(responseId?: string): void {
  if (responseId === undefined) {
    this.currentResponseId++;  // 1. 自增门控
    
    // 2. 丢弃所有陈旧块
    for (const [key, entry] of this.scheduled) {
      try {
        entry.src.stop();  // 3. 停止播放
      } catch {}
      this.scheduled.delete(key);
    }
    this.nextStartTime = 0;
  }
}
```

**enqueue时的检查**（adapter-web/src/player.ts:57-61）：
```typescript
enqueue(chunk: PlaybackChunk): boolean {
  if (Number(chunk.responseId) <= this.currentResponseId) {
    this.stats.droppedStale++;
    return false;  // 直接丢弃
  }
  // ...
}
```

**形式化证明（TLA+）**：
- 规约：`interrupt()` 完成后不存在 `responseId < current` 的播放事件
- 模型检验：验证所有可能的状态转换

### Q9: getScheduledEndTime有什么用？

**问题本质**：决定何时解除静麦（unmute）

**场景**：
- 用户打断AI → AI停止播放 → 用户开始说话
- 如果AI还在播放 → 用户说话会被回声淹没

**方案**：
```typescript
// 对话场景
async function handleBargeIn() {
  player.interrupt();
  
  const endTime = player.getScheduledEndTime();
  if (endTime) {
    // 等待当前播放块结束
    await new Promise(r => setTimeout(r, (endTime - ctx.currentTime) * 1000));
  }
  
  // 确认无音频播放后，解除静麦
  capture.unmute();
}
```

**代码证据**（adapter-web/src/player.ts:143-149）：
```typescript
getScheduledEndTime(responseId?: string): number | null {
  const matching = responseId
    ? [...this.scheduled.values()].filter((e) => e.responseId === responseId)
    : [...this.scheduled.values()];
  if (matching.length === 0) return null;
  return matching.reduce((m, e) => Math.max(m, e.endTime), 0);
}
```

## 四、传输与重连

### Q10: 为什么不用Socket.IO默认重连？

**问题本质**：固定重连策略不适合弱网

**Socket.IO的问题**：
```javascript
reconnectionAttempts: 5,
reconnectionDelay: 1000,
// 5秒后放弃，弱网下太短
```

**抖动指数退避方案**（core-transport-ws/src/index.ts:29-37）：
```typescript
export function nextReconnectDelay(attempt: number, baseMs: number, maxMs: number): number {
  const exp = baseMs * Math.pow(2, attempt);
  const jittered = exp * (0.5 + Math.random() * 0.5);  // 抖动
  return Math.min(jittered, maxMs);
}
```

**为什么加抖动？**
- 避免多客户端同时重连 → 雷鸣群效应
- 随机化让重连错开

**参数调优**：
- `baseMs = 1000`（1秒首次重连）
- `maxMs = 30000`（最长等待30秒）
- 重连次数：无上限（除非用户主动关闭）

### Q11: 背压感知如何实现？

**问题本质**：防止 `socket.send()` 无限堆积内存

**WebSocket的bufferedAmount**：
```typescript
ws.send(data);
console.log(ws.bufferedAmount);  // 未发送的字节数
```

**监控方案**（core-transport-ws/src/index.ts:264-274）：
```typescript
private checkBackpressure(): void {
  const buffered = this.ws.bufferedAmount;
  if (!this.bpHigh && buffered > this.bp.highWaterBytes) {
    this.bpHigh = true;
    this.bp.onPressure(true);  // 通知上层暂停生产
  } else if (this.bpHigh && buffered < this.bp.lowWaterBytes) {
    this.bpHigh = false;
    this.bp.onPressure(false);  // 通知上层恢复
  }
}
```

**上层响应**：
- **转写场景**：捕获层切环形丢弃模式（保留最新N ms）
- **对话场景**：静麦 + UI警告（丢弃会破坏语义）

## 五、协议与编解码

### Q12: Volcengine v3/sauc协议如何实现？

**问题本质**：无公开文档，凭抓包+Python源码参考

**帧结构**：
```
byte 0: 0x11 (协议版本1)
byte 1: (msgType << 4) | flags
  - msgType: 1=配置, 2=音频
  - flags: 0=无, 1=有序列号, 2=最后一帧
byte 2: (serialization << 4) | compression
  - serialization: 1=JSON
  - compression: 0=无, 1=gzip
byte 3: 0x00 (保留)
bytes 4-7: payload size (big-endian)
bytes 8+: payload
```

**编码实现**（provider-doubao/src/codec.ts:76-89）：
```typescript
export function encodeFullClientRequest(payload: Record<string, unknown>): ArrayBuffer {
  const jsonBytes = new TextEncoder().encode(JSON.stringify(payload));
  const { body, compression } = maybeGzip(jsonBytes);

  const out = new Uint8Array(8 + body.length);
  out[0] = 0x11;
  out[1] = (MSG_TYPE_FULL_REQUEST << 4) | FLAG_NONE;
  out[2] = (SERIAL_JSON << 4) | compression;
  out[3] = 0x00;
  const dv = new DataView(out.buffer);
  dv.setUint32(4, body.length, false);  // big-endian
  out.set(body, 8);
  return out.buffer;
}
```

**解码实现**（provider-doubao/src/codec.ts:144-182）：
```typescript
export function parseServerResponse(buf: ArrayBuffer): ServerResponse | null {
  const bytes = new Uint8Array(buf);
  if (bytes[0] !== 0x11) return null;

  const msgType = (bytes[1] >> 4) & 0x0f;
  const flags = bytes[1] & 0x0f;
  const compression = bytes[2] & 0x0f;

  // 可选的4字节序列号
  let offset = 4;
  if (flags & FLAG_HAS_SEQ) {
    seq = new DataView(bytes.buffer).getInt32(offset, false);
    offset += 4;
  }

  const size = new DataView(bytes.buffer).getUint32(offset, false);
  const body = bytes.slice(offset + 4, offset + 4 + size);
  const decompressed = maybeGunzip(body, compression);

  return { msgType, flags, compression, seq, payload: JSON.parse(decompressed) };
}
```

## 七、简历陈述示例

### 项目介绍（1分钟）

> "voice-kit是我把多年语音前端经验沉淀成的跨端SDK——把实时对话的Barge-in竞态、流式ASR的乱序去重、端到端延迟观测这些'每个语音应用都要重写一遍的脏活'，做成可移植的核心包加可替换的端适配器。30+ npm包公开发布，覆盖Web、小程序、Electron三端。"

### 技术亮点追问应对

**面试官**："你说Barge-in竞态消除，具体怎么做的？"

**回答**：
> "这个问题本质是三层队列的原子中断——等待队列、解码队列、播放队列。我的方案是用responseId做门控：
> 
> 第一，每个播放块携带responseId，interrupt()时自增currentResponseId；
> 
> 第二，enqueue时检查，陈旧块直接丢弃；
> 
> 第三，AudioBufferSourceNode.stop()停止当前播放；
> 
> 最后，等onended触发才emit barge-in-complete。
> 
> 我还写了TLA+形式化规约，模型检验证明interrupt完成后不存在陈旧播放事件。"

**面试官**："为什么不用AbortController？"

**回答**：
> "AudioBufferSourceNode不支持取消已调度的start()，只能stop()。AbortController适合Promise链，但音频播放不在Promise链上——它是事件驱动的。"
