## 二、每个项目单独的技术深挖

### 2.1 行中导游：前端在「AI音频内容生成」中的独特价值

#### 表层看：好像是后端的事
路线计算 → POI匹配 → LLM生成剧本 → TTS合成音频。看起来全部是后端逻辑，前端只是播放器。

#### 深层看：前端的真正战场

**战场1：流式音频编排与缓存策略**

这不是一个简单的音频播放器。它是一个**动态的、分段生产、实时拼接**的音频流系统：

```
时间轴上的挑战：
  t=0        t=5min      t=10min       t=15min
  ├──────────┼───────────┼─────────────┼──────────
  播放        触发下一段    触发下一段     路线变更
  segment_1   生产          生产          重新匹配POI
               segment_2     segment_3     → 覆盖播放计划

实际要处理的情况：
- 路线偏离原计划（导航改道、用户绕路）
  → 当前segment播放到一半，需要自然中断还是播完？
  → 新路线POI列表已变，如何无缝切换？
- segment生产延迟（LLM生成超过5分钟）
  → 需要「安全垫」机制：预留静默/音乐过渡
  → 降级策略：减少生成复杂度保速度
- 音频缓冲管理
  → 预加载多少段？何时清理已播放的？
  → 结合行车网络不稳定（隧道、高速切换基站）
```

**面试里的技术点：**
> 「我设计了一个动态音频调度引擎，核心是用『滑动窗口+预生产+优雅降级』策略解决三个冲突：路线实时变化 vs 内容预生产、LLM生成延迟 vs 无缝播放、弱网场景 vs 音频流畅度。具体实现上，维护一个3段窗口（当前+下一段+下下段），每段覆盖5分钟，用状态机管理窗口的填充、切换和废弃。」

**战场2：地图+音频的时空同步可视化**

这是一个被忽略但极其适合前端炫技的点：

```
车的实时GPS位置 → 在地图上以动画标注
当前播放的POI → 在地图上高亮范围圈
下一段即将播放的POI → 地图上虚线连接/预览
已播放的POI → 灰色标记保留轨迹

技术挑战：
- 地图上同时展示：历史轨迹 + 当前POI圈 + 未来路线 + 实时GPS点
  → 数据更新频率：GPS 1Hz, 路线变更 事件驱动, 播放进度 音频timeupdate事件
  → 如何避免React重新渲染导致地图闪烁？
- POI圈与实际地形的匹配
  → 不是简单圆形，要贴合实际道路和建筑形状
  → 地图SDK的碰撞检测 vs 前端的Haversine简算
```

**战场3：双人播客的交互式控制**

PRD里提到音频风格对标小宇宙播客，这意味着前端播放器需要超越简单audio标签：

- **跳过/重听当前POI讲解**：不打断整体播放流，只控制当前segment
- **切换主题模式**：「我不想听历史了，换成美食模式」→ 中断当前，触发新主题内容生产
- **标记/收藏讲解**：「这段讲得好，收藏下来分享」
- **进度可视化**：当前行程总共有多少POI？播放到第几个？剩余多少？

**简历级表述：**
> 「主导设计了行中导游的前端架构，核心挑战不是播放音频，而是在『路线动态变化 + AI内容延迟生产 + 弱网环境』三重约束下实现无缝的音频体验。我设计了一套动态音频调度引擎，基于滑动窗口+状态机模式，解决内容预生产和路线实时变化的冲突。同时构建了地图与音频的时空同步可视化系统，让用户直观感知『AI正在讲解窗外哪个方向的那栋建筑』。」

### 2.2 在哪儿：把「调一个多模态API」升维成「推理可视化系统」

#### 表层看
用户上传图片 → 调用多模态模型 → 返回位置。看起来前端只需要一个图片上传组件 + markdown渲染。

#### 深层看：这才是真正的战场

**战场1：AI推理过程的可视化（最核心的差异化）**

PRD里写了关键技术要求：

> 「推理逻辑链要能根据难易情况调整」
> 「多轮分析、多轮网络搜索」
> 「基于图片细节去分析、搜索、推理」

这意味着**不是一次API调用返回结果**，而是一个**多步骤推理链条**。这正是你做SSE流式可视化的经验可以直接发挥的地方：

```
用户上传一张「没有明显地标的街景照片」

AI推理过程（流式展示）：
┌─────────────────────────────────────────────┐
│ 🔍 第1步：图像分析                          │
│   ├─ 识别到建筑风格：南方骑楼风格            │
│   ├─ 检测到文字：招牌上有「粵」字样          │
│   ├─ 植物特征：路边有棕榈树                 │
│   └─ 推断：华南沿海城市                     │
├─────────────────────────────────────────────┤
│ 🌐 第2步：网络搜索                          │
│   ├─ 搜索「骑楼 棕榈树 街区」               │
│   ├─ 匹配到：广州上下九、厦门中山路          │
│   └─ 缩小到2个候选                           │
├─────────────────────────────────────────────┤
│ 🔬 第3步：细节对比                          │
│   ├─ 对比招牌字体→ 更接近广州样式            │
│   ├─ 对比路面铺装→ 匹配上下九步行街          │
│   └─ 确认：广州上下九步行街                  │
├─────────────────────────────────────────────┤
│ 📍 结果：广州市荔湾区上下九步行街            │
│    ┌──────────────────────────┐             │
│    │    [地图卡片]             │             │
│    │    距离你 3.2km           │             │
│    │    开放时间：全天          │             │
│    │    特色：骑楼建筑群        │             │
│    └──────────────────────────┘             │
└─────────────────────────────────────────────┘
```

**这个推理可视化一旦做出来，面试时打开小程序demo一下，效果碾压一切「我调了个API」的简历。**

具体实现：
- SSE推送每一步推理 → 前端用ReactFlow/自定义动画展示推理树
- 关键图片细节的标注（检测到的文字、识别的建筑）在图片上高亮
- 中间搜索结果（候选地点列表）用地图散点展示
- 最终确认结果的过渡动画：候选点逐个淘汰，最终定位

**战场2：竞品调研暴露的前端机会**

你的PRD竞品分析结论非常有价值：

| 竞品 | 优势 | 前端缺陷（=你的机会） |
|------|------|---------------------|
| 夸克 | 准确率~70%（图搜图能力强） | 推理过程黑盒，用户不知道为什么是这个结果 |
| o3 | 多步推理能力强 | 纯文本输出，没有地图可视化 |
| 点点 | 回复格式好 | 没有推理过程展示、没有地图+图片联动 |

**三个竞品在各自的维度强，但没有一个做了「推理过程可视化 + 地图卡片 + 图片细节标注联动」。**

而你的项目背景（滴滴）天然有地图能力优势，这是任何外部竞品都没有的。

**战场3：小程序端的性能极限挑战**

PRD的指标：
> 推理首token：1-2s
> 简单case：回复不超过3s
> 复杂case：回复不超过15s

在小程序环境下的挑战：
- 小程序不支持SSE（需要WebSocket模拟或分片轮询）
- 图片上传+压缩要在小程序端完成（微信限制单文件大小）
- EXIF提取要在小程序端做（微信API限制）
- 地图组件在小程序中的性能瓶颈

**简历级表述：**
> 「在微信小程序环境下，实现了多模态AI的流式推理可视化系统。核心创新在于将AI的多步推理过程（图像分析→网络搜索→细节对比→定位确认）实时可视化展示，让用户理解『AI是怎么一步步找到这个地点的』。解决了三个工程难题：小程序不支持SSE情况下的流式数据模拟、图片细节自动标注与地图卡片的时空联动、以及小程序WebView中地图标注的高性能渲染。」

> 「我的角色是从前端视角定义产品技术架构，确保三个产品的技术方案有最大程度的复用，同时每个产品在各自场景下做到体验极致。

> **第二层，流式AI推理可视化（最核心的创新）：** 在「在哪儿」项目中，我没有满足于「调API返回结果」，而是将AI的多步推理过程——图像分析、关键词提取、网络搜索、候选对比、最终定位——实时流式可视化。用户可以看到AI是怎么一步步推理的，每一步匹配到的图片细节在照片上高亮标注。这个设计让产品的信任感和科技感大幅提升。竞品无一做到这一点。

> **第三层，动态内容调度引擎：** 在「行中导游」项目中，我面对的核心挑战是「路线实时变化 vs 内容预生产」的冲突。我设计了滑动窗口+状态机的调度方案，预生产3个窗口（15分钟）的音频内容，窗口滑动时自动触发下一段生产，路线变更时触发窗口废弃和重新规划。同时考虑了弱网环境的缓存降级策略。

> **第四层，从产品到平台：** 当前正在基于前两个产品的经验，构建通用化的AI图搜平台，将「在哪儿」的单点推理能力泛化为多模态视觉搜索，将「行中导游」的动态调度能力泛化为AI工作流编排。三个产品共享基础设施，但各自在前端体验层有独立创新。」

| 3 | SSE流式事件调度器 | 共用 | 通用流式推送调度器，支持SSE乱序处理、幂等状态机、小程序环境降级 |
| 4 | 地图+多媒体时空同步 | 行中导游 | 地图GPS坐标与音频播放进度的毫秒级同步可视化 |
| 5 | 小程序AI推理流式交互 | 在哪儿 | 在不支持SSE的小程序环境实现流式AI推理交互 |
| 6 | 多模态Agent编排引擎 | 共用 | 可配置的多步骤LLM调用链，支持条件分支、重试策略、并行调度 |
| 7 | 多模态RAG知识库 | 共用 | 统一管理POI数据、图片特征向量、文本embedding的多模态检索系统 |
| 8 | 弱网环境的内容缓存+降级 | 行中导游 | 行车场景下的预加载、分段缓存、网络状态自适应降级策略 |

### 4.2 面试必问的技术决策（提前准备话术）

**Q1: 三个产品技术方案最大的共性和差异是什么？**

> 「共性在于底层都依赖Agent编排、流式推送和Geo计算。差异在于对这三项能力的偏重不同——行中导游偏重调度（时序复杂度最高），在哪儿偏重可视化（交互复杂度最高），AI图搜偏重检索（数据复杂度最高）。所以我在设计基础设施时用了『核心通用 + 扩展点开放』的架构，每个产品在扩展点做差异化实现。」

**Q2: 在哪儿为什么不直接调一个多模态API返回结果？**

> 「因为我们做了竞品分析，夸克准确率70%、豆包50%，但即便是最好的竞品也没有让用户理解『为什么是这个结果』。在多模态AI准确率有限的前提下，展示推理过程有两个价值：第一，如果推理过程合理但结果错了，用户会理解并自主判断；第二，推理过程本身就是最好的科技感和差异化体验。这是纯技术判断不能替代的产品思维。」

**Q3: 小程序不支持SSE怎么解决？**

> 「三种降级策略：1）WebSocket模拟（需要后端支持，且小程序WebSocket有连接数限制）；2）分片轮询（前端定时请求结果，后端缓存中间状态）；3）混合方案——有WebSocket能力的场景用WebSocket，降级场景用智能轮询（根据推理步骤耗时动态调整轮询间隔）。最终选型视后端能力而定。」

## 六、最终建议：三个产品的定位和优先级

### 6.1 在面试中怎么讲

**不要逐一介绍三个项目。**用一个主线串起来：

> 「我过去一年围绕『AI视觉理解 + 地理空间智能』这条主线做了三件事：
>
> 第一件事是『在哪儿』——一个根据照片识别地点的小程序。这个项目让我深入理解了多模态AI的实际能力边界，也发现了一个关键的体验缺口：**所有竞品都在追求准确率，没有人关心推理过程的可解释性**。所以我重点做了推理可视化，这是这个项目最核心的前端创新。
>
> 第二件事是『行中导游』—— 一个根据行车路线自动生成播客式讲解的AI音频产品。这个项目的核心前端挑战不是播放音频，而是**在路线实时变化和AI生成延迟之间找到平衡**。我设计了一套动态调度引擎来应对。
>
> 第三件事是正在推进的AI图搜平台——这是前两个项目的自然延伸。『在哪儿』是基于图片找地点，AI图搜是基于任何条件找任何图片，是前者的泛化；『行中导游』的动态调度经验可以直接用于图搜的流式结果推送。三个产品共享一套基础设施，但各自在体验层有独立的创新。」

### 6.2 如果你只能重点做一个

**优先做「在哪儿」的推理可视化。**理由：

1. 它已经上线了（有数据、有用户、有说服力）
2. 推理可视化是你最有差异化的前端创新（竞品全都没做）
3. 视觉效果好，面试Demo效果炸裂
4. 前端工作量最大、技术最深（SSE流式、地图标注、图片细节高亮、推理树动画）
5. 做完后可以直接复用框架到AI图搜

### 6.3 「在哪儿」推理可视化的具体实现路径

```
Phase 1: 推理步骤流式展示 (1-2周)
  - SSE推送每步推理，前端动画展示
  - 步骤状态机：pending → running → done
  - 并行步骤支持（第2步可并行搜多个来源）

Phase 2: 图片细节联动标注 (1-2周)
  - 推理步骤中提到「识别到招牌文字」
    → 图片上自动高亮框标注该区域
  - 提到「植物特征」
    → 图片上对应区域放大镜效果

Phase 3: 地图候选点可视化 (1周)
  - 中间推理产生的候选地点列表 → 地图散点
  - 逐步缩小范围的过程动画

Phase 4: 封装为通用推理可视化SDK
  - 不限于「在哪儿」，任何多步AI推理都可接
  - → 直接复用到AI图搜的渐进式搜索
```
