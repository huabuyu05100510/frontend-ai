# 简历路径选项 A / B / C

> **模型**：Claude (Sonnet 4.5)
> **场景**：「网页翻译」项目作为 10 年前端专家代表作的定位选项
> **目的**：把三条路并排摆出来，便于比较决策，**不是推荐某一条**

---

## 共同前提（不随路径变化）

无论走哪条路，**当前「占位符 + 云 LLM」方案已经做的事**都是基础：
- 占位符 schema（`⟦tN⟧`）+ 属性隔离
- 三层 XSS 防御链（tag 白名单 / attr 黑名单 / URL 协议白名单）
- benchmark 24 case 对标 DeepL（标签保留率 98.3% vs 93.3%）
- TDD + e2e + UI 回归工程纪律

**三条路的差异在「基础之上做什么」。**

---

## 路 A：把翻译做透，加深度（中等难度）

### 定位
「**优秀的高级工程师作品**」— 工程能力证明，能过 80% 面试，但不让人惊艳。

### 核心增量
| 项 | 价值 | 工期 |
|---|---|---|
| 流式翻译（SSE） | 首字延迟 < 500ms（vs 当前 1.3s 整段） | 1 周 |
| 性能监控 dashboard | FPS / 内存 / 翻译覆盖率 / 错误率 | 1-2 周 |
| 多模型路由 | MiniMax / DeepL / Azure 按场景切换 | 1 周 |
| 标注功能 | 双语对照 + 生词标记 + 导出 | 2-3 周 |
| 翻译记忆 | 重复段落不重译，缓存命中率 | 1 周 |

**总工期**：6-8 周

### 优点
- 全部基于现有架构扩展，**风险低**
- 每个增量独立可交付，节奏稳
- 标注功能是 CLAUDE.md 里已经写过的方向

### 缺点
- 每个点都是「**业界面试题**」级别，不是「**面试官接不住**」级别
- 流式 / 监控 / 路由 都是工程基本功，没有稀缺性
- 简历杀伤力：**3 / 5**

### 简历叙事
> 网页翻译扩展：流式翻译（SSE，首字 < 500ms）、多模型路由、翻译记忆（缓存命中率 X%）、性能可观测（FPS / 内存 / 错误率 dashboard）、双语标注导出。TDD + e2e + UI 回归全覆盖。

→ 面试官反应：「工程做得很扎实」（但不会主动追着问技术细节）

---

## 路 B：换赛道，做真正难的事（高难度）

### 定位
「**代表作**」— 有论文级深度，能让人记住。

### 候选方向（任选其一打穿，不要全做）

#### B1：词级对齐可视化（推荐）
- 本地跑 NMT，拿 attention 矩阵投影到前端
- hover 中文词 → 高亮英文原文
- **DeepL / Google / 沉浸式翻译结构上做不到**（云架构不暴露 attention）
- 详见 `docs/local-translation-tech-plan-V1.md` 模块 A
- **工期**：MVP 5 周

#### B2：CRDT 协同翻译记忆
- 网页改了一段只重翻译那一段（增量更新）
- 多设备翻译记忆同步（CRDT）
- **不是「缓存」，是「内容变更感知」**
- **工期**：6-8 周

#### B3：WebGPU 本地 NMT
- 浏览器内跑量化模型，离线 / 隐私场景
- 企业付费意愿强（不上传）
- 详见 `docs/local-translation-tech-plan-V1.md` 模块 B
- **工期**：MVP 3-4 周

### B1 + B3 合并（最优组合）
- WebGPU 本地 NMT 是地基
- 词级对齐是地基派生的杀手锏
- **两者天然耦合，一起做成本最低、故事最完整**
- 总工期：5-7 周

### 优点
- **稀缺性最高**：会 transformer + wasm + 前端可视化的人极少
- **护城河深**：基于结构差异，不是优化细节
- **可演示**：demo 一放出来面试官就懂

### 缺点
- **高风险**：transformers.js 可能不暴露 attention（需 PoC 验证）
- **工期长**：5-7 周 vs 路 A 的 6-8 周（但路 B 单点打穿，路 A 是多点铺开）
- **学习曲线陡**：要补 ML / transformer 知识
- 简历杀伤力：**5 / 5**

### 简历叙事
> 基于 WebGPU 的浏览器内 NMT 翻译 + 词级对齐可视化。本地跑量化模型，离线可用；利用 transformer cross-attention 矩阵投影实现词级 src↔tgt 对齐，准确率 X%（WPT-21 评估集）。该功能因云架构限制，DeepL / Google / 沉浸式翻译**结构上不可实现**。

→ 面试官反应：「这个怎么做的？attention 矩阵怎么聚合的？」（主动追问 = 稀缺性证据）

## 路 C：诚实定位（不是"不做"，是"换框架"）

### 定位
**放弃「代表作」单点定位，改「工程作品集」组合定位。**

### 核心思路
单个项目不封神，**用 2-3 个项目凑成 portfolio**：
- 网页翻译：工程纪律展示（TDD + e2e + 可观测）
- 配合 `work.md` 里过往项目（待盘点）
- 第三个项目：可选做一个有深度的（如 B1）

### 翻译项目在这个框架下的角色
**不追求技术深度，追求工程完整度**：
- 把现有功能做干净
- benchmark + 性能 + 错误监控做齐
- 文档写全（已有基础）
- **不强行加 ML / WebGPU**

### 优点
- **风险最低**：不踩新技术坑
- **省精力**：用省下的时间做其他项目 / 生活 / 副业
- **诚实**：不自欺欺人地包装

### 缺点
- **没有杀手锏**：作品集里每个项目都「不错但不出彩」
- 招高端岗（P7+ / staff engineer）时**穿透力不够**
- 简历杀伤力：**3 / 5**（但分散在多个项目）

### 简历叙事
> 工程作品集：网页翻译扩展（占位符 + XSS 防御 + benchmark）+ [项目 2] + [项目 3]。每个项目体现不同的工程能力（工程纪律 / 性能优化 / 架构设计）。

→ 面试官反应：「项目挺多，讲一个你最得意的」（没有立刻抓住眼球的点）

## 三条路对比

| 维度 | 路 A（加深度） | 路 B（换赛道） | 路 C（组合定位） |
|---|---|---|---|
| **工期** | 6-8 周 | 5-7 周（单点） | 3-4 周 + 其他项目 |
| **风险** | 低 | 高（PoC 可能失败） | 最低 |
| **稀缺性** | 中（工程基本功） | 高（结构差异） | 低（多点铺开） |
| **简历杀伤力** | 3/5 | 5/5 | 3/5（单点） |
| **适合岗位** | 中高级前端 | 高级 / Staff / ML+前端 | 中高级前端 |
| **学习曲线** | 平 | 陡（ML / transformer） | 平 |
| **失败兜底** | 仍有完整作品 | PoC 失败归档为调研 | 总有作品 |

## 决策矩阵

### 选 A 如果：
- 时间有限（< 2 个月）
- 不想碰 ML
- 目标岗位是中高级前端（不是 staff）
- 想要稳定交付

### 选 B 如果：
- 有 5-7 周完整时间
- 愿意学 transformer / wasm
- 目标岗位是 staff / 资深 / ML+前端交叉岗
- 想要一个能让人记住的项目

### 选 C 如果：
- 不想把鸡蛋放一个篮子
- 有其他项目可以配套
- 目标岗位是中高级前端
- 重视工作生活平衡

### 混合策略（推荐考虑）
**B1 + C 的混合**：
- 主力做 B1（词级对齐 MVP，5 周）
- 同时把翻译项目其他维度做干净（路 A 的「流式翻译」「性能监控」顺手做）
- 不强求 B3（WebGPU 全套），用 wasm 跑通对齐就够
- 最终作品集：1 个有深度的 + 工程完整度高的翻译项目

→ 简历既有稀缺性，又有完整度。

---

## 我的判断（诚实）

**路 A 单独走不划算** — 6-8 周换 3/5 杀伤力，性价比低。

**路 C 是兜底** — 即使 B 失败，C 总能落地。

**路 B 是唯一能打出差异化的路**，但前提是 PoC 验证通过。

**最优解是 B + C 混合**：
- All in B1（词级对齐），用 wasm 不强求 WebGPU
- 同时把翻译项目工程化做完整（顺带的路 A 增量）
- B1 失败 → 退回路 C（已经有完整作品）

→ **风险可控，上限最高。**
