# 第一章：项目是什么？能做什么？

## 1.1 一句话介绍

**妙码 AI 引擎** 是一个「可视化 AI 工作流编辑器」。

用户可以在画布上拖拽节点、连线，像搭积木一样组装 AI 流程，然后一键运行。

```
用户拖拽界面                    背后执行引擎
┌──────────────────────────┐   ┌────────────────────────────────┐
│  [开始] → [AI大模型]      │   │  1. 验证工作流合法性            │
│             ↓             │   │  2. 拓扑排序确定执行顺序        │
│         [意图识别]        │   │  3. 逐节点执行                  │
│          /        \       │   │  4. 条件分支选路                │
│    [查订单]    [答问题]    │   │  5. 节点间传递数据              │
│       ↓            ↓     │   │  6. 返回最终结果                │
│    [结束]       [结束]    │   └────────────────────────────────┘
└──────────────────────────┘
```

## 1.2 项目目录结构

```
miaoma-aiflow-v2/
├── apps/
│   └── workflow/                  ← Next.js 前端应用（画布 + 设置面板）
```

# 第二章：前端画布（可视化编辑器）

## 2.1 技术选型：React Flow

画布用的是 **@xyflow/react**（就是 React Flow），它是专门做流程图的库。

核心概念只有两个：

- **Node（节点）**：画布上的方块，比如 `[AI大模型]`、`[意图识别]`
- **Edge（连线）**：节点之间的箭头

```tsx
// 每个节点长这样（数据结构）
{
    id: 'llm-1',           // 唯一 ID
    type: 'llm',           // 节点类型，决定用哪个组件渲染
    data: {
        label: '大模型处理',
        config: {           // 节点配置，用户在右侧表单填写
            model: 'qwen3.5:9b',
            systemPrompt: '你是一个智能助手',
            userPrompt: '用户问：${start-1.question}',
        }
    }
}
```

## 2.2 画布节点组件：LLMNode

**文件：** `apps/workflow/components/flow/nodes/llm-node.tsx`

这个组件只负责**在画布上显示**，不做任何逻辑计算。

```tsx
export function LLMNode({ data, selected }: NodeProps) {
    // data.config 就是用户填写的配置
    const model = (data?.config as any)?.model ?? 'qwen3.5:9b'
    const label = (data?.label as string) || '大模型'

    return (
        // selected 为 true 时显示紫色边框（被点击选中）
        <div className={`... ${selected ? 'border-purple-700' : 'border-transparent'}`}>

            {/* 节点头部：图标 + 名称 */}
            <div className="flex items-center mb-3">
                <div className="bg-purple-700 ...">
                    <ICON_MAP.llm size={14} />   {/* 大脑图标 */}
                </div>
                <span>{label}</span>
            </div>

            {/* 显示当前选择的模型名 */}
            <span>{model}</span>

            {/* 左侧连接点（接收上游数据）*/}
            <Handle type="target" position={Position.Left} />

            {/* 右侧连接点（输出给下游）*/}
            <Handle type="source" position={Position.Right} />
        </div>
    )
}
```

**Handle 是什么？**

Handle 就是节点边上那个小圆点，用来连线。

- `type="target"` = 左边的点，接收输入
- `type="source"` = 右边的点，输出数据

```
                ┌──────────────────┐
   上游节点 ──●─→│  🧠 大模型节点    │─●──→ 下游节点
     target↗   └──────────────────┘  ↖source
```

## 2.3 右侧设置面板：LLMSettingsForm

**文件：** `apps/workflow/components/flow/settings/forms/llm-settings-form.tsx`

用户点击节点后，右侧弹出配置表单。表单用的是 **react-hook-form**。

### 为什么用 react-hook-form？

普通受控组件（`useState`）的问题：每次输入一个字符，整个表单都重新渲染。
react-hook-form 通过非受控组件 + 内部订阅，**只更新变化的那个字段**，性能更好。

### Controller 和 register 怎么选？

```tsx
// ✅ 原生 HTML input → 用 register（直接绑定 DOM）
<Input
    type="number"
    {...register('temperature', { valueAsNumber: true })}
/>

// ✅ 自定义组件（比如富文本编辑器）→ 用 Controller（中间层代理）
<Controller
    name="systemPrompt"
    control={control}
    render={({ field }) => (
        // field.value 和 field.onChange 由 react-hook-form 控制
        <VariableEditor
            value={field.value}
            onChange={field.onChange}
        />
    )}
/>
```

原因：`register` 通过 `ref` 直接操作 DOM，但自定义组件没有原生 DOM，所以用 `Controller` 做中间代理。

### 自动保存是怎么工作的？

```tsx
// 核心：监听表单变化，防抖后自动保存
useFormAutoSaveWithControl(control, onSave, true)

// 内部原理（简化版）：
function useFormAutoSaveWithControl(control, onSave) {
    const values = useWatch({ control })  // 订阅表单所有字段变化

    useEffect(() => {
        const timer = setTimeout(() => {
            onSave(values)  // 300ms 内没有新变化，才保存
        }, 300)

        return () => clearTimeout(timer)  // 有新变化，取消上一次计时
    }, [values])
}
```

**流程示意：**

```
用户输入 "你" → 取消计时，重新计300ms
用户输入 "好" → 取消计时，重新计300ms
用户输入 "啊" → 取消计时，重新计300ms
300ms 无操作   → 触发保存！调用 onSave({ systemPrompt: "你好啊" })
```

## 2.4 意图节点设置：ConditionSettingsForm

**文件：** `apps/workflow/components/flow/settings/forms/condition-settings-form.tsx`

这个表单不用 react-hook-form，而是纯 `useState`，自己实现了防抖自动保存。

```tsx
const autoSaveTimerRef = useRef<NodeJS.Timeout | null>(null)
const lastSavedDataRef = useRef<string>('')  // 记录上次保存的内容

useEffect(() => {
    // 1. 把当前状态序列化成字符串
    const currentDataStr = JSON.stringify({ model, intents })

    // 2. 和上次保存的比较，一样就不保存（防重复请求）
    if (currentDataStr === lastSavedDataRef.current) return

    // 3. 清除上一次的计时器（防抖核心）
    if (autoSaveTimerRef.current) clearTimeout(autoSaveTimerRef.current)

    // 4. 开启新计时器
    autoSaveTimerRef.current = setTimeout(() => {
        // 过滤掉名称为空的意图（用户还没填完）
        const validIntents = intents.filter(i => i.name.trim())
        onSave?.({ model, intents: validIntents })

        // 5. 记录本次保存内容，供下次 diff 比较
        lastSavedDataRef.current = JSON.stringify({ model, intents: validIntents })
    }, 500)

    // 6. 组件卸载时清理计时器
    return () => { if (autoSaveTimerRef.current) clearTimeout(autoSaveTimerRef.current) }
}, [model, intents, onSave])
```

**为什么用 `useRef` 存计时器而不是 `useState`？**

因为 `setState` 会触发重渲染，而我们只需要记录计时器 ID，不需要触发 UI 更新，用 `useRef` 更合适。

# 第三章：工作流执行引擎（核心）

## 3.1 引擎的职责

**文件：** `packages/ai-engine/src/core/engine.ts`

引擎就像一个「工厂流水线的总调度」，它做这几件事：

```
接收工作流定义 + 输入参数
        ↓
①  验证工作流（格式对不对，节点配置有没有填）
        ↓
②  构建执行图（把节点和连线整理成图数据结构）
        ↓
③  拓扑排序（确定谁先执行谁后执行）
        ↓
④  按顺序逐个执行节点
        ↓
⑤  收集结果，返回给调用者
```

## 3.2 GraphBuilder：DAG 图构建器

**文件：** `packages/ai-engine/src/core/graph-builder.ts`

**DAG** = Directed Acyclic Graph，有向无环图。工作流就是一个 DAG：

- **有向**：连线有方向（从上游流向下游）
- **无环**：不能形成循环（A→B→C→A 这种不允许）

### 邻接表是什么？

```
工作流定义：
  节点：start-1, llm-1, condition-1, http-1, end-order, end-tech
  连线：start-1→llm-1, llm-1→condition-1, condition-1→http-1, ...

转成邻接表（谁指向谁）：
  adjacencyList = {
      'start-1':     ['llm-1'],
      'llm-1':       ['condition-1'],
      'condition-1': ['http-1', 'end-tech'],   // 两个出口（两个意图分支）
      'http-1':      ['end-order'],
      'end-order':   [],
      'end-tech':    [],
  }

反向邻接表（谁指向我）：
  reverseAdjacencyList = {
      'start-1':     [],              // 没有上游，是起点
      'llm-1':       ['start-1'],
      'condition-1': ['llm-1'],
      'http-1':      ['condition-1'],
      'end-order':   ['http-1'],
      'end-tech':    ['condition-1'],
  }

入度表（有几个节点指向我）：
  inDegree = {
      'start-1':     0,   // 没有人指向我 → 起始节点
      'llm-1':       1,
      'condition-1': 1,
      'http-1':      1,
      'end-order':   1,
      'end-tech':    1,
  }
```

### Kahn 算法（拓扑排序）

目标：确定节点执行顺序，保证所有上游先执行完，再执行当前节点。

```
算法步骤：

初始状态：
  队列 = [start-1]   （入度为 0 的节点）
  已执行 = []

第1轮：出队 start-1
  执行 start-1
  已执行 = [start-1]
  start-1 的后继是 llm-1，llm-1 入度 1-1=0 → 入队
  队列 = [llm-1]

第2轮：出队 llm-1
  执行 llm-1
  已执行 = [start-1, llm-1]
  llm-1 的后继是 condition-1，入度 1-1=0 → 入队
  队列 = [condition-1]

第3轮：出队 condition-1
  执行 condition-1（LLM 意图识别）
  结果：matchedBranch = 'intent-0'（查询订单）
  → 触发分支剪枝，把 end-tech 子树排除掉

第4轮：出队 http-1
  执行 http-1（发 HTTP 请求查订单）

第5轮：出队 end-order
  执行 end-order（收集结果）

最终执行顺序：[start-1, llm-1, condition-1, http-1, end-order]
end-tech 被剪枝，不执行
```

### 分支剪枝是怎么工作的？

```
条件节点执行完后，知道选了哪个分支：

condition-1 的两条出边：
  edge: condition-1 --[intent-0]--> http-1    （查询订单分支）
  edge: condition-1 --[intent-1]--> end-tech  （技术问题分支）

选择了 intent-0（查询订单），所以排除 intent-1 这条线的所有下游：

excludeSubtree('end-tech'):
  end-tech 加入 excludedNodes ✓
  end-tech 没有后继，结束

重新拓扑排序时，excludedNodes 里的节点直接跳过 ✓
```

## 3.3 变量解析：`${nodeId.key}` 是怎么工作的？

工作流中，节点可以引用其他节点的输出：

```
// 用户在 userPrompt 里写：
"用户 ${start-1.userName} 问：${start-1.question}"

// 执行时，引擎把它替换成实际值：
"用户 MiaoMa 问：请帮我查询订单状态"
```

**变量解析器原理：**

```typescript
// 正则匹配 ${nodeId.outputKey} 格式
function resolveText(template: string, variables: Record<string, unknown>): string {
    return template.replace(/\$\{([^}]+)\}/g, (match, path) => {
        // path = "start-1.userName"
        const [nodeId, ...keys] = path.split('.')
        const nodeOutputs = variables[nodeId]  // 从上下文取 start-1 的输出
        // 按 key 路径取值
        const value = keys.reduce((obj, key) => obj?.[key], nodeOutputs)
        return value !== undefined ? String(value) : match
    })
}
```

# 第四章：节点执行器详解

每种节点类型对应一个执行器类，全部继承 `BaseNodeExecutor`。

## 4.1 LLM 执行器

**调用 Ollama 本地大模型：**

```typescript
// 构建多轮对话消息
const messages = [
    // System：设定 AI 角色
    { role: 'system', content: '你是一个智能助手...' },
    // User：用户问题（已经过变量替换）
    { role: 'user', content: '用户 MiaoMa 问：请帮我查询订单状态' },
    // Assistant（可选）：预设回答开头，引导输出格式
    // { role: 'assistant', content: '好的，我来查询...' }
]

// 调用 Ollama REST API
POST http://localhost:11434/api/chat
{
    model: 'qwen3.5:9b',
    stream: false,
    messages: [...],
    options: { temperature: 0.7, num_predict: 2000 }
}

// 返回结果
{
    output: 'AI 的回答文本',
    tokens: 150  // 消耗的 token 数
}
```

**temperature 参数说明：**

```
temperature = 0.0  → 确定性输出，每次回答一样（适合做数据提取）
temperature = 0.7  → 适度随机（适合正常对话）
temperature = 1.5  → 高度随机，有创意但可能乱说（适合创作）
```

## 4.2 Condition 执行器（意图识别）

这是整个系统最有意思的节点，用 LLM 来做「分类器」。

```
工作流程：
1. 获取上游节点（LLM节点）的输出文本
2. 构建意图识别提示词
3. 调用 LLM（temperature=0，保证确定性输出）
4. 解析 LLM 返回的 JSON
5. 根据匹配结果，告诉引擎走哪条分支
```

**提示词构建：**

```
System Prompt：
你是一个意图识别助手。分析用户输入并识别其意图。
可能的意图列表：
1. 查询订单：用户问关于查询订单状态、物流信息等
2. 技术问题：用户问关于技术问题需要帮助

请严格按照以下 JSON 格式返回，不要添加任何其他内容：
{"intent": "意图名称", "confidence": 0.95}

User Prompt：
请分析以下用户输入，判断其意图：
用户输入：请帮我查询订单状态
```

**LLM 返回：**

```json
{"intent": "查询订单", "confidence": 0.97}
```

**解析逻辑（含容错）：**

```typescript
try {
    // 正常路径：提取 JSON 并解析
    const jsonMatch = content.match(/\{[\s\S]*\}/)
    const parsed = JSON.parse(jsonMatch[0])
    matchedIntent = parsed.intent        // "查询订单"
    confidence = parsed.confidence       // 0.97
} catch {
    // 容错路径1：LLM 没有输出标准 JSON，直接在文本里找意图名
    for (const intent of intents) {
        if (content.includes(intent.name)) {
            matchedIntent = intent.name
            confidence = 0.5  // 置信度给低一点
            break
        }
    }
}

// 容错路径2：什么都没匹配到，用第一个意图作为默认
if (!matchedIntent && intents.length > 0) {
    matchedIntent = intents[0].name
    confidence = 0.3
}
```

**最终路由：**

```typescript
// "查询订单" 在意图列表里是第 0 个
const intentIndex = intents.findIndex(i => i.name === '查询订单')  // → 0
const branchId = `intent-${intentIndex}`  // → "intent-0"

// 返回给引擎，告诉它走 intent-0 这条边
return { matchedBranch: 'intent-0', outputs: { matchedIntent, confidence } }
```

# 第五章：插件系统

## 5.1 为什么需要插件系统？

内置节点（LLM、HTTP、条件等）是固定的，但用户可能需要各种各样的自定义功能：

- 发短信
- 查数据库
- 调用第三方 API

插件系统让开发者可以**扩展节点类型**，就像 VS Code 插件扩展编辑器功能一样。

## 5.2 插件系统整体架构

```
插件生命周期：

开发阶段：
  插件开发者 → 编写插件代码（executor.js + manifest.json）→ 发布到 CDN

安装阶段：
  用户 → 在「插件市场」安装插件
  → 数据库记录：{ pluginId, version, permissions, manifestUrl, executorUrl }

执行阶段：
  工作流运行时
  → 发现节点类型是 "plugin:email-sender:send"
  → 从 DB 查安装记录
  → 从 CDN 加载插件代码
  → 在沙箱中执行
```

## 5.3 插件节点类型命名规则

```
普通节点：  "llm"、"http"、"condition"
插件节点：  "plugin:email-sender:send"
            ↑        ↑           ↑
         前缀   插件ID(包名)   节点类型

parsePluginNodeType("plugin:email-sender:send")
→ { pluginId: "email-sender", nodeType: "send" }
```

## 5.4 权限沙箱（最重要的安全机制）

**文件：** `packages/plugin-runtime/src/sandbox/permission-proxy.ts`

插件代码是第三方写的，不能完全信任。沙箱通过**权限代理**限制插件能做什么。

**5 种权限：**


| 权限               | 允许做什么      |
| ---------------- | ---------- |
| `network`        | 发送 HTTP 请求 |
| `env:read`       | 读取环境变量     |
| `email:send`     | 发送邮件       |
| `llm:invoke`     | 调用 LLM 模型  |
| `knowledge:read` | 搜索知识库      |


**代理拦截原理：**

```typescript
// 没有权限时直接报错，插件无法绕过
function createPermissionProxy(config) {
    function checkPermission(permission, action) {
        if (!grantedPermissions.includes(permission)) {
            throw new PermissionDeniedError(permission, action)
        }
    }

    return {
        // 插件调用 services.fetch(...) 时
        fetch: async (input, init) => {
            checkPermission('network', 'fetch')    // ← 先检查权限
            // 通过后才真正执行
            headers.set('X-Plugin-Id', pluginId)   // ← 加上插件标识
            return services.fetch(input, { ...init, headers })
        },

        // 插件调用 services.invokeLLM(...) 时
        invokeLLM: async (options) => {
            checkPermission('llm:invoke', 'invokeLLM')  // ← 先检查权限
            return services.invokeLLM(options)
        },

        // ... 其他服务同理
    }
}
```

**形象比喻：**

```
插件 = 来访客人
沙箱 = 门禁系统

客人想进会议室（network）→ 检查门卡，有权限才开门
客人想进机房（knowledge:read）→ 检查门卡，没权限直接拒绝
```

## 5.5 插件注册到引擎的完整流程

```typescript
    // 第1步：扫描工作流，找出所有插件节点

        .filter(Boolean)
    // → ['email-sender', 'current-time']

    // 第2步：从数据库查这些插件的安装记录
    const installations = await prisma.pluginInstallation.findMany({
        where: { userId, isEnabled: true, plugin: { pluginId: { in: pluginIds } } },
        include: { plugin: true, version: true }
    })
    // → [{ pluginId: 'email-sender', executorUrl: 'https://cdn/.../executor.js', permissions: ['email:send'] }]

    // 第3步：创建插件加载器
    const loader = new PluginLoader({ services: createWorkflowPluginHostServices(userId) })

    // 第4步：逐个加载插件并注册到引擎
    for (const installation of installations) {
        // 从 CDN 下载插件代码，创建沙箱
        const module = await loader.loadFromUrls({ ...installation })

        // 把插件节点注册到引擎的节点注册中心
        engine.getRegistry().register('plugin:email-sender:send', {
            execute: async (nodeId, config, context) => {
                return module.executors.get('send').execute({ config, services: module.sandbox.getServices() })
            }
        })
    }
}
```

# 第六章：知识库 RAG 系统

## 6.1 什么是 RAG？

RAG = Retrieval Augmented Generation（检索增强生成）

**问题背景：** LLM 的知识有截止日期，不知道你公司内部的文档。

**RAG 的解法：**

```
用户问：我们公司的请假流程是什么？

                    ↓
          从知识库里找相关文档

  知识库
  ├── 员工手册.pdf          ← 找到相关片段："年假申请需提前3天..."
  ├── 考勤制度.docx         ← 找到相关片段："病假需上传医院证明..."
  └── 入职指南.md

                    ↓
  把找到的文档片段 + 用户问题一起发给 LLM：

  "以下是公司文档：
   年假申请需提前3天...病假需上传医院证明...
   请根据以上文档回答：我们公司的请假流程是什么？"

                    ↓
  LLM 根据实际文档内容回答，不再瞎编
```

## 6.2 Hybrid RAG：两种检索方式的结合

**文件：** `packages/ai-engine/src/knowledge/retriever/hybrid-retriever.ts`

### 向量检索（语义搜索）

```
工作原理：
  1. 把文档切成小块（chunks），每块约 500 字
  2. 用 Embedding 模型把文字转成数字向量
     "年假申请" → [0.12, -0.34, 0.89, ...]  (1024个数字)
  3. 把所有文档向量存入 Qdrant（向量数据库）

  搜索时：
  1. 把问题也转成向量
     "请假怎么申请" → [0.11, -0.31, 0.91, ...]
  2. 在 Qdrant 里找向量最相似的文档块（余弦相似度）

优点：能理解语义，"请假"和"休假"能匹配上
缺点：对精确词语不敏感，搜"HR系统V2.0"可能找不到
```

### 全文检索（关键词搜索）

```
工作原理：BM25 算法（改进版的 TF-IDF）
  TF（词频）：这个词在文档里出现几次
  IDF（逆文档频率）：这个词有多稀有（越稀有越重要）

优点：精确匹配关键词，找"HR系统V2.0"百发百中
缺点：不懂语义，"请假"搜不到含"休假"的文档
```

### 混合检索（Hybrid）

```typescript
const retriever = createHybridRetriever(embeddingService, vectorStore, fulltextProvider)

const results = await retriever.retrieve({
    query: '请假流程',
    mode: 'hybrid',
    topK: 5,
    threshold: 0.6,      // 相关度低于 0.6 的丢弃
    vectorWeight: 0.7,   // 70% 向量分数 + 30% 关键词分数
})
```

```
向量检索结果：        全文检索结果：
  文档A  得分0.89       文档A  得分0.91
  文档B  得分0.75       文档C  得分0.85
  文档C  得分0.70       文档B  得分0.60

混合融合（vectorWeight=0.7）：
  文档A：0.89*0.7 + 0.91*0.3 = 0.623 + 0.273 = 0.896
  文档B：0.75*0.7 + 0.60*0.3 = 0.525 + 0.180 = 0.705
  文档C：0.70*0.7 + 0.85*0.3 = 0.490 + 0.255 = 0.745

最终排名：文档A > 文档C > 文档B
```

# 第七章：数据流动全链路

## 7.1 节点间如何传递数据？

每个节点执行完后，把结果存入 **ExecutionContext** 的变量表：

```
执行上下文（ExecutionContext）
└── variables（变量表）
    ├── 'start-1' → { userName: 'MiaoMa', question: '请帮我查询订单' }
    ├── 'llm-1'   → { output: 'AI的回答', tokens: 150 }
    └── 'condition-1' → { matchedIntent: '查询订单', confidence: 0.97 }
```

**下游节点读取上游数据的方式：**

1. **显式引用**（在配置中写 `${nodeId.key}`）
  ```
   userPrompt: "用户 ${start-1.userName} 问：${start-1.question}"
   → 执行时替换为: "用户 MiaoMa 问：请帮我查询订单"
  ```
2. **隐式继承**（引擎自动把上游输出合并给下游输入）
  ```typescript
   // 引擎在执行节点前，自动收集上游输出
   for (const upstreamId of context.getUpstreamNodes(node.id)) {
       const outputs = context.variables.getNodeOutputs(upstreamId)
       Object.assign(nodeInputs, outputs)  // 合并到当前节点的 inputs
   }
  ```

# 第九章：技术架构设计模式

## 9.1 策略模式（Strategy Pattern）：节点注册中心

```typescript
// 注册中心：一个 Map，类型字符串 → 执行器对象
class NodeRegistry {
    private executors = new Map<string, NodeExecutor>()

    register(type: string, executor: NodeExecutor) {
        this.executors.set(type, executor)
    }

    get(type: string): NodeExecutor | undefined {
        return this.executors.get(type)
    }
}

// 注册内置节点
registry.register('llm', new LLMExecutor())
registry.register('http', new HttpExecutor())
registry.register('condition', new ConditionExecutor())

// 运行时，根据节点类型动态获取执行器
const executor = registry.get(node.type)  // 多态调用
executor.execute(nodeId, config, context, logger)
```

**好处：** 增加新节点类型，只需新增一个执行器类并注册，不需要修改引擎核心代码（开闭原则）。

## 9.2 代理模式（Proxy Pattern）：权限沙箱

```
原始服务                代理层（PermissionProxy）         插件
fetch()    ←─────  checkPermission('network') + fetch    ←── 插件调用
invokeLLM()  ←───  checkPermission('llm:invoke') + ...   ←── 插件调用
sendEmail()  ←───  checkPermission('email:send') + ...   ←── 插件调用
```

插件始终只能看到代理，看不到原始服务，权限检查无法绕过。

## 9.3 模板方法模式：BaseNodeExecutor

```typescript
// 基类定义执行骨架
abstract class BaseNodeExecutor<TConfig> {
    async execute(nodeId, config, context, logger): Promise<NodeExecutionResult> {
        logger.nodeStart(nodeId, this.type, config)    // ← 统一的开始日志
        const startedAt = Date.now()

        try {
            // ← 子类实现具体逻辑
            const result = await this.doExecute(nodeId, config, context, logger)
            logger.nodeEnd(nodeId, result)             // ← 统一的结束日志
            return { ...result, duration: Date.now() - startedAt }
        } catch (error) {
            // ← 统一的错误处理
            return { success: false, error, duration: Date.now() - startedAt }
        }
    }

    // 子类只需实现这个方法
    protected abstract doExecute(...): Promise<NodeExecutionResult>
}

// LLMExecutor 只关心业务逻辑
class LLMExecutor extends BaseNodeExecutor<LLMNodeConfig> {
    protected async doExecute(nodeId, config, context, logger) {
        // 只写调用 LLM 的逻辑
    }
}
```

# 第十章：常见面试问题完整答案

## Q1：这个项目最大的技术挑战是什么？

**答：**

有两个核心挑战：

**第一，工作流的执行顺序控制。** 工作流是个有向无环图（DAG），节点之间有依赖关系，必须等上游节点执行完才能执行下游节点。同时还有条件分支，需要动态选择执行路径。我们用 Kahn 算法做拓扑排序确定初始执行顺序，条件节点执行后再通过 `selectBranch` 递归排除未选中分支的子树，重新排序。

**第二，插件系统的安全隔离。** 插件是第三方代码，不能直接给它访问系统资源的权限。我们用代理模式实现了权限沙箱，插件调用任何服务（网络、LLM、邮件、知识库）时都会经过 `PermissionProxy` 的权限检查，没有声明对应权限就直接抛异常，插件无法绕过。

## Q2：React Hook Form 的 Controller 和 register 有什么区别，什么时候用哪个？

**答：**

`register` 通过 `ref` 直接操作原生 DOM 元素，适用于 `<input>`、`<select>`、`<textarea>` 这些原生表单元素。

`Controller` 是一个包装器组件，通过 `field.value` 和 `field.onChange` 把 react-hook-form 的状态传给自定义组件，适用于自定义的富文本编辑器、日期选择器、下拉组件等没有原生 DOM ref 的组件。

选择规则很简单：如果是原生 HTML 表单元素用 `register`，自定义组件用 `Controller`。

## Q3：防抖自动保存怎么实现的，为什么用 useRef 存计时器？

**答：**

防抖的核心是：用户停止操作一段时间后才触发保存，避免每次键盘输入都发请求。

实现方式：在 `useEffect` 里用 `setTimeout` 设置延迟，同时用 `clearTimeout` 取消上一次的计时器。关键点是这个计时器 ID 必须在组件重渲染间保持稳定，所以用 `useRef` 存储，而不是 `useState`。

用 `useState` 存计时器的问题是：设置新计时器 ID 会调用 `setTimer()` → 触发重渲染 → 重渲染又触发 `useEffect` → 进入无限循环。`useRef` 的 `.current` 是一个可变引用，修改它不会触发重渲染，完全规避这个问题。

## Q4：Hybrid RAG 是什么，为什么比单独用向量检索效果好？

**答：**

向量检索把文本转成数字向量，通过计算向量相似度来找相关文档，擅长语义理解，"请假"能匹配到"休假"。但对精确关键词不敏感，比如产品编号、人名、版本号这类专有词汇效果差。

全文检索基于 BM25 算法，精确匹配关键词，但不理解语义，"我想休息两天"无法匹配"请假申请流程"。

Hybrid RAG 把两种结果按权重融合，通过 `vectorWeight` 参数（比如 0.7）控制比例：70% 取向量得分 + 30% 取关键词得分。实际测试中，混合检索在覆盖专业词汇的同时保留了语义理解能力，召回率通常比单一方式提升 10-20%。

## Q5：如果让你优化这个系统，你会从哪里入手？

**答：**

三个方向：

1. **并行执行**：目前节点是串行执行的，但没有依赖关系的节点（比如两个并行的 HTTP 请求）可以并发执行，用 `Promise.all` 大幅缩短总耗时。
2. **流式输出**：LLM 的回答是逐 token 生成的，目前是等全部生成完才返回。改成流式（server-sent events 或 WebSocket）可以让用户看到 AI 逐字输出，体验更好。
3. **执行历史持久化**：目前执行日志只在内存里，刷新页面就没了。应该持久化到数据库，支持查看历史执行记录和回放节点输入输出。
